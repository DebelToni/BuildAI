Core Functionality – User Stories

The following stories capture WHY each major feature exists, in the language of the people who use BuildAI.

Training Workflow

  • Story T‑1: As an ML researcher, I want to start a new transformer training run with one CLI command so that I can iterate on model architectures quickly.
  • Story T‑2: As an infra engineer, I want training metrics pushed to Weights & Biases so that I can monitor loss curves in real time.

Inference & Serving

  • Story I‑1: As a product engineer, I want a REST endpoint compatible with the OpenAI API so that I can swap BuildAI in place of GPT‑4 with minimal code changes.
  • Story I‑2: As a researcher, I want KV‑cache reuse across requests so that I can benchmark long‑context inference without restarting the model.

LADA – Developer Assistant

  • Story L‑1: As a developer, I want to ask the assistant to refactor a function while seeing diffs inline so that I can accept or reject each change.
  • Story L‑2: As a security‑conscious user, I want to run LADA fully offline so that no proprietary code leaves my laptop.
  • Story L‑3: As a project manager, I want to see the assistant’s planning steps so that I can trust how it arrived at a solution.

Deployment & Ops

  • Story D‑1: As a DevOps engineer, I want a Terraform module that spins up GPU nodes on RunPod so that I can match capacity to demand.
  • Story D‑2: As an open‑source contributor, I want CI to run unit tests on every PR so that main stays green.

Extensibility

  • Story E‑1: As a plugin author, I want a documented Python hook to register new model backends so that BuildAI can talk to my custom inference server.
  • Story E‑2: As a researcher, I want to swap the attention implementation without touching the training script so that I can benchmark experimental kernels.
